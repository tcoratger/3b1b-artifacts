Ethereum networking, state of the art · October 2026

    Ethereum's networking stack

    Every Ethereum node is two programs with two peer-to-peer networks. This page takes both apart, floor by floor: how a node finds peers, how it opens an encrypted channel, which messages cross it, and the bytes each message is made of.

    It describes mainnet after Fusaka and its blob-parameter forks (PeerDAS live, 14 blobs target, 21 maximum), with eth/69 to eth/72, snap/2 and Glamsterdam (on testnets) marked where they change the picture. It is the baseline for a redesign: Section 13 lists where the stack strains.

    You need: what a blockchain block and a transaction are, what a hash function and a public/private key pair do. Everything else is built here.
    You will build: a map of both stacks; the exact bytes of a node record, a gossip topic, a request and a data column; and a list of where the design strains, with numbers.
    Colours: execution layer (devp2p) · consensus layer (libp2p) · Engine API · transactions · blocks · blobs, cells, columns · keys and what breaks.

    1One slot, two networks

    Since the Merge in September 2022, an Ethereum node is a pair of programs. The execution layer (EL) client, such as Geth, Nethermind, Besu, Erigon or Reth, holds the account state, runs transactions and keeps the pool of pending transactions. The consensus layer (CL) client, such as Lighthouse, Prysm, Teku, Nimbus, Lodestar or Grandine, follows proof of stake: it tracks validators, chooses the head of the chain and finalizes it. The two halves of one node talk over a local HTTP connection, the Engine API.

    The two layers are upgraded together, and each upgrade has two names, one per layer. The upgrade activated on 3 December 2025 is Fulu on the consensus layer and Osaka on the execution layer, together Fusaka. The next one, Glamsterdam, is Gloas plus Amsterdam. Between upgrades, small blob-parameter-only (BPO) forks change only how many blobs a block may carry. Version numbers such as eth/69 or snap/2 name versions of individual wire protocols; Section 6 introduces them.

    Each half also talks to the world, and they do it through two separate networks. The EL speaks devp2p, the stack Ethereum has used since 2015. The CL speaks libp2p, a modular stack adopted for the beacon chain in 2020. A node therefore has two network identities, listens on two sets of ports and keeps two lists of peers.

    Figure 1 follows the objects of one 12-second slot through a toy network of six nodes. The top row is the six EL halves, the bottom row their CL twins, and the purple links are each node's Engine API. Watch which row each object travels on.

    Three observations from Figure 1 organise the rest of the page. First, the two networks carry disjoint objects: a transaction never touches libp2p, and an attestation (a validator's vote on the chain) never touches devp2p. Second, both networks use two styles of communication. Push (gossip) spreads new objects to everyone as fast as possible; pull (request/response) fetches specific objects from one peer, for a node that is catching up or missed something. Third, below the messages, each network needs the same floors: a way to find peers, a way to prove who you are and encrypt, and a way to run several conversations over one connection.

    2The two towers

    A networking stack is a pile of layers, each using the one below it. Figure 2 draws the two piles side by side, from the floor (finding peers) to the roof (the messages the client cares about). Tap a floor to read what it does and which section takes it apart.

    Read the floors from the bottom. Discovery answers "who is out there?" with a distributed table of node records on UDP. The node record says how to reach a node and what it serves. The transport is TCP, and for libp2p also QUIC over UDP. The handshake proves each side holds the private key behind its identity and derives session keys; everything afterwards is encrypted. Multiplexing lets several protocols share one connection. The application protocols are the messages: transactions and blocks for the EL, gossip topics and request/response for the CL. The encoding turns objects into bytes: RLP for the EL, SSZ for the CL, both compressed with Snappy, a fast compression format.

    Figure 3 is the same information indexed by object instead of by floor: for every object the chain moves, the path it takes. Read the empty cells too: nothing a validator signs goes through devp2p, and since the Merge no block travels on devp2p gossip at all.

    3Who is a peer: keys, node IDs and records

    Before two machines can talk they need names. On both networks a node's name comes from a key pair on the secp256k1 elliptic curve, the same curve that signs Ethereum transactions. The node keeps the private key secret and publishes the public key.

    Definition 1 · Node ID

    The node ID of a node with public key point \((x, y)\) is the 256-bit number \(\mathrm{id} = \mathrm{keccak256}(x \,\|\, y)\), where \(x\) and \(y\) are each written as 32 big-endian bytes.

    Hashing spreads the IDs uniformly over the 256-bit space, which discovery (Section 4) relies on. A node's ID cannot be chosen freely: changing it means generating a new key.

    An ID says nothing about where the node is. That is the job of the node record.

    Definition 2 · Ethereum Node Record (ENR, EIP-778)

    An ENR is the RLP list \([\,\mathit{sig}, \mathit{seq}, k_1, v_1, k_2, v_2, \dots]\) with the keys \(k_i\) sorted and unique, at most 300 bytes in total. \(\mathit{seq}\) is a counter the owner increases on every change. Under the identity scheme "v4", \(\mathit{sig}\) is the 64-byte secp256k1 signature of \(\mathrm{keccak256}(\mathrm{rlp}([\mathit{seq}, k_1, v_1, \dots]))\) by the node's key.

    Because the record is signed, anyone can relay it and nobody can alter it. Because it carries a sequence number, a peer that sees a higher \(\mathit{seq}\) knows to fetch the new version. Figure 4 opens the test record from EIP-778 byte by byte. It is the running example node for the rest of the page.

    Example 1 · Reading the record

    1. The text form enr:-IS4QHCY…dl8 is enr: followed by the record in URL-safe base64. Decoding gives 134 bytes starting f8 84: an RLP list whose body is 0x84 = 132 bytes long.
    2. The first element, b8 40 + 64 bytes, is the signature. Then 01: \(\mathit{seq} = 1\).
    3. Four pairs follow in sorted key order: id = "v4", ip = 7f000001 (127.0.0.1), secp256k1 = 03ca634c…3138 (a 33-byte compressed public key), udp = 765f (port 30303).
    4. Decompress the key to \((x, y)\) and hash: \(\mathrm{keccak256}(x\|y) = \)a448f24c6d18e575…ec94617f7. The signature verifies against this key.

    Check: the sizes in Figure 4 add up:

    \[ 2 + 66 + 1 + (3+3) + (3+5) + (10+34) + (4+3) = 134. \]

    The test record carries only an address. Real records carry more, and the two layers use different keys. Figure 5 lays out what an EL record and a CL record add. The CL record is a small advertisement (its fields are explained in Sections 7 and 9): a peer can tell from the record alone which fork the node follows, which attestation subnets it serves and how many data columns it stores, before opening a connection.

    4Finding peers: a table sorted by XOR

    A new node knows a handful of hard-coded bootnodes. From them it must find thousands of others, without any server keeping a list. Both layers solve this with Kademlia, a distributed hash table in which each node keeps records of a few peers, chosen so that any node can be reached in a few hops.

    Definition 3 · Distance and log-distance

    The distance between node IDs \(a\) and \(b\) is \(a \oplus b\), their bitwise XOR read as a number. The log-distance is the bit length of \(a \oplus b\): the position of the highest bit where \(a\) and \(b\) differ, counting positions from 1 at the lowest bit. It ranges from 0 (same ID) to 256.

    A node sorts the peers it knows into buckets, one per log-distance, and keeps at most \(k = 16\) records per bucket. Half of all IDs differ from yours in the top bit, a quarter agree on the top bit and differ in the second, and so on, so the far buckets fill instantly and the near ones stay almost empty. The table thus holds many coarse pointers to the far half of the ID space and fine pointers near home. Figure 6 shows it on 8-bit IDs.

    To find nodes near a target ID, a node runs an iterative lookup. It asks the \(\alpha = 3\) closest nodes it knows for their records near the target. Each answer comes from a node closer to the target, whose own near buckets are finer, so each round of answers is closer still. With \(n\) nodes the lookup ends in about \(\log_2 n\) rounds in the worst case and far fewer in practice. Discovery runs lookups toward random targets in a loop, which walks the whole network and fills the table.

    Two wire protocols: discv4 and discv5

    Kademlia is the algorithm. The wire protocol is the format of the UDP packets that carry it, and Ethereum has two. discv4 (2015) is used only by execution clients. Its packets are plaintext: a hash, a 65-byte signature, a type byte and an RLP body. Its FINDNODE names a target public key, and nodes answer with NEIGHBORS. Anyone on the path can read and record who is asking for what.

    discv5 (v5.1) is used by every consensus client and, alongside discv4 on the same port, by Geth and Reth. It encrypts every packet with AES-GCM under a session key, hides even the packet header, and asks by log-distance: FINDNODE [255, 256] means "send me your records in buckets 255 and 256". It also carries TALKREQ/TALKRESP, a slot for other protocols to ride on the same sockets; the Portal network for light execution clients uses it. Figure 8 compares the two packets.

    Encryption needs a shared key, and two nodes that have never met have none. discv5 makes one on demand with the exchange in Figure 9. Node A sends its request encrypted under a key B cannot know yet. B cannot decrypt it, so it answers WHOAREYOU with a random challenge. A then sends a handshake packet: a fresh ephemeral public key, a signature over the challenge by its node key (the ID signature, which proves A owns its ID), its ENR if B's copy is stale, and the original request, now encrypted under keys both sides derive by Diffie–Hellman.

    A consensus client wants more than any peer. It needs peers on the gossip subnets it serves, and peers that store the data columns it samples (Section 9). Since discv5 has no search by service, the client runs ordinary random lookups and filters the records it gets by their attnets and cgc fields. Figure 10 shows the filter. A subnet that few nodes serve takes many lookups to fill, which is one reason clients keep large peer counts.

    5Opening a channel

    Discovery yields an address. The next floor turns a TCP connection to that address into an authenticated, encrypted channel that several protocols can share. The two layers built this floor independently, and it is where they differ most.

    devp2p: RLPx

    RLPx is a protocol designed for Ethereum in 2014. The dialer knows the recipient's public key from its record, so it can encrypt its first message to it directly with ECIES: combine a fresh ephemeral key with the recipient's public key by Diffie–Hellman and use the result as an encryption key. Figure 11 plays the exchange.

    The key schedule fits in four lines. With \(e\) the ECDH result of the two ephemeral keys and \(n_A, n_B\) the nonces:

    \[ \begin{aligned} \mathit{shared} &= \mathrm{keccak256}\big(e \,\|\, \mathrm{keccak256}(n_B \,\|\, n_A)\big) \\ \class{c-red}{\mathit{aes}} &= \mathrm{keccak256}(e \,\|\, \mathit{shared}) \\ \class{c-red}{\mathit{mac}} &= \mathrm{keccak256}(e \,\|\, \class{c-red}{\mathit{aes}}) \\ \text{frame} &= \mathrm{AES256\text{-}CTR}_{\class{c-red}{\mathit{aes}}}(\text{header} \| \text{body}) \text{ with Keccak MACs keyed by } \class{c-red}{\mathit{mac}} \end{aligned} \]

    The same \(\mathit{aes}\) key and the same counter start encrypt both directions. The RLPx specification lists this under "known issues": two keystreams are identical, so a known plaintext in one direction exposes the matching bytes in the other. It has stayed because changing it means changing every client at once.

    After the handshake each side sends Hello: protocol version 5, a client name, and its capabilities, such as eth/69 and snap/2. From then on every message is Snappy-compressed. One connection carries all shared capabilities, and RLPx tells them apart by message number alone, through the rule of Figure 12.

    libp2p: negotiate, then Noise, then streams

    libp2p builds the same floor from separate, named parts, and negotiates each part by name with multistream-select: one side proposes a protocol string such as /noise, the other echoes it to accept. Over TCP the sequence is in Figure 13. The security part is the Noise framework with the XX pattern: three messages that exchange ephemeral and static X25519 keys (Diffie–Hellman on Curve25519) and derive session keys for ChaCha20-Poly1305, an authenticated cipher. Inside the handshake each side also sends its libp2p identity key, a secp256k1 key, and a signature with it over its Noise static key, which ties the encrypted channel to the peer's identity.

    The multiplexer, yamux (or the older mplex, which the specification still lists), splits the connection into numbered streams with their own flow control. Gossip uses one long-lived stream per peer in each direction; every request/response exchange opens a fresh stream and closes it when done.

    The consensus specification also requires QUIC, and clients prefer it when a peer advertises a quic port. QUIC runs over UDP and merges the transport handshake with a TLS 1.3 handshake, whose certificate carries the libp2p identity key. Its streams are native, so the separate security and muxer negotiations disappear, and a lost packet stalls one stream instead of all of them. Figure 14 counts the round trips before the first request can be sent.

    6What execution clients say to each other

    Once RLPx is up, execution clients speak two application protocols. eth carries the transaction pool and the chain history. snap serves a recent copy of the state to nodes that are syncing. Neither carries new blocks any more: since the Merge, blocks arrive from the consensus layer through the Engine API, and the old NewBlock and NewBlockHashes messages keep their message numbers but must be ignored (the faded cells of Figure 12).

    The first eth message on a connection is Status. In eth/69 it is the list

    \[ [\mathit{version}, \mathit{networkid}, \mathit{genesis}, \mathit{forkid}, \mathit{earliest}, \mathit{latest}, \mathit{latestHash}]. \]

    The fork identifier (EIP-2124) is a checksum of the genesis hash and every past fork block, plus the next scheduled fork, so two nodes on incompatible chains disconnect after one message. The last three fields say which blocks the node can serve, a range that changes as nodes prune history.

    The transaction pool

    A transaction enters the network when a wallet sends it to some node's JSON-RPC endpoint. That node must get it to the next proposers' pools fast, without every node sending every transaction to every peer. eth does it in two tiers. The node sends the full transaction to a few peers (Geth uses the square root of its peer count) and only a hash announcement to the rest. Since eth/68 an announcement carries the type and size next to the hash, so a peer can decide whether it wants the transaction before asking for it with GetPooledTransactions.

    Blob transactions are never pushed in full. Each blob is 128 KiB, and since Fusaka the transaction also carries 128 cell proofs per blob (Section 9). EIP-4844 requires nodes to announce them and let peers pull. Figure 15 shows both tiers.

    A 6-blob transaction is 786,432 bytes of blob data and 768 cell proofs of 48 bytes, about 0.8 MB, and every full node used to download all of it. eth/72 (EIP-8070, the "sparse blobpool", a draft in Glamsterdam discussions with a Geth prototype) cuts that. Its announcement adds a 16-byte bitmap of the cells the sender holds, and a new GetCells message fetches selected cells. Each node downloads a whole blob with probability \(p \ge 0.15\); otherwise it downloads only the cells of the columns its consensus client stores (Section 9), and only after two peers announced full availability. Figure 16 measures the saving.

    History and state

    A node that joins must also obtain the past. Block headers, bodies and receipts come over eth with paired requests: GetBlockHeaders/BlockHeaders, GetBlockBodies/BlockBodies, GetReceipts/Receipts. eth/69 removed the bloom filter from receipts on the wire (the receiver recomputes it), and eth/70 lets a peer return one block's receipts across several messages, because a block with a high gas limit can produce more than the 10 MiB message limit.

    Not every node holds all of history. Since July 2025 clients may drop everything before the Merge block, 15,537,394, and serve it instead from archive files. eth/69 makes this visible: Status carries the range a node serves, and BlockRangeUpdate moves it. Figure 17 shows a syncing node picking a peer for one block.

    Replaying every block since genesis to rebuild the state takes days. snap skips it. A node picks a recent block, the pivot, and downloads that block's state directly as sorted ranges of accounts with GetAccountRange, along with storage and contract code. Each response comes with Merkle proofs at the range edges, so it can be checked against the pivot's state root. Peers keep snapshots for only the last 128 blocks, so the pivot must move forward as the chain grows, and the ranges already downloaded become slightly stale.

    snap/1 fixed the stale parts by healing: walking the state trie from the new root and fetching any node that differed, one round trip per trie level. snap/2 (EIP-8189, with Glamsterdam) replaces healing with block-level access lists (BALs): each block lists every account and slot it touched with the new values, so the syncing node fetches the BALs since the first pivot and applies them as patches. Figure 18 runs both endings.

    7Gossip on the consensus layer

    The consensus layer moves objects every slot that every node must see within seconds: the block, its data, and about a million votes per epoch. It uses gossipsub, a publish–subscribe protocol from libp2p. Messages are grouped into topics; a node subscribes to some topics and receives every message published on them.

    Definition 4 · Mesh and gossip

    For each topic, every subscribed node keeps a mesh of \(D = 8\) subscribed peers (allowed between \(D_\text{low} = 6\) and \(D_\text{high} = 12\), repaired every 0.7 s heartbeat). A new valid message is forwarded in full to all mesh peers except the one it came from. At each heartbeat a node also sends IHAVE lists of recent message IDs to \(D_\text{lazy} = 6\) non-mesh peers, which can ask for any they missed with IWANT.

    The mesh delivers fast, in about \(\log_{D-1} n\) hops. The price is duplicates: every node receives each message from several mesh neighbours, up to \(D\) copies, and only the first is useful. For a 240-byte vote that is cheap. For a 45 kB data column it is the dominant cost. Gossipsub v1.2 adds IDONTWANT: on receiving a large message, a node immediately tells its mesh peers not to send it, so copies that have not started yet are cancelled. Publish a message in Figure 19 and count the duplicates.

    A node forwards a message only after validating it, and every topic has its own rules: a block must come from the expected proposer with a valid BLS signature (the signature scheme of all consensus messages, on the BLS12-381 curve, whose signatures on the same message can be merged into one), a vote must be from a committee member and not a duplicate. Validation returns accept (forward), ignore (drop silently) or reject (drop and lower the sender's score). This per-hop check is what stops spam, and it adds its own delay at every hop.

    Each peer has a score (gossipsub v1.1) built from time in the mesh, first deliveries, missing deliveries, invalid messages and IP colocation. Low scorers are pruned from meshes and eventually disconnected. Ethereum's messages carry no libp2p signature or sequence number (the StrictNoSign policy); a message is identified by a hash of its content, defined below.

    Topics and message IDs

    A topic name says what the messages are, which fork they belong to, and how they are encoded:

    \[ \texttt{/eth2/}\underbrace{\class{c-blue}{\texttt{8c9f62fe}}}_{\text{fork digest}}\texttt{/}\underbrace{\class{c-yellow}{\texttt{beacon\_attestation\_17}}}_{\text{name}}\texttt{/}\underbrace{\texttt{ssz\_snappy}}_{\text{encoding}} \]

    The fork digest is 4 bytes that change at every fork, so nodes on different forks cannot mix messages even if they connect. It is the first 4 bytes of \(\mathrm{sha256}(\mathit{fork\_version} \,\|\, \mathit{genesis\_validators\_root})\); since Fulu it is also XORed with a hash of the current blob parameters, so every blob-parameter fork changes it too.     Votes: subnets and aggregation

    With about a million validators, each attesting once per 32-slot epoch, the network handles about 30,000 votes per slot. Sending all of them to everyone would cost about 7 MB per node per slot. Instead the votes of each committee go to one of 64 attestation subnets, and only nodes subscribed to that subnet see them. A few members of each committee, about 16 chosen by a verifiable lottery, act as aggregators: they collect the votes on their subnet, merge them into one BLS aggregate signature, and publish it on the global beacon_aggregate_and_proof topic. The next proposer packs aggregates into its block. Figure 21 follows one committee's votes.

    Each node also serves two subnets permanently, so every subnet has a stable population for its votes to pass through. The two subnets are computed from the node ID and rotate every 256 epochs, at a moment offset by the node ID so that the whole network does not reshuffle at once. Figure 22 runs the computation for the running example node.

    Definition 5 · Long-lived subnets

    Let \(\mathit{prefix} = \mathrm{id} \gg 250\) (the top 6 bits) and \(\mathit{off} = \mathrm{id} \bmod 256\). At epoch \(E\), with seed \(s = \mathrm{sha256}\big(\lfloor (E + \mathit{off})/256 \rfloor\big)\), the node's subnets are \(\pi_s(\mathit{prefix})\) and \(\pi_s(\mathit{prefix}) + 1 \bmod 64\), where \(\pi_s\) is the 90-round swap-or-not shuffle on 64 positions.

    8Asking one peer: request/response

    Gossip delivers what is new. A node that was offline, has just started, or missed a message must ask for it. Consensus clients do this with request/response: open a new stream, name the protocol, send one request, read the response chunks, close the stream. The protocol ID names everything at once:

    \[ \texttt{/eth2/beacon\_chain/req/}\underbrace{\texttt{beacon\_blocks\_by\_range}}_{\text{message}}\texttt{/}\underbrace{\texttt{2}}_{\text{version}}\texttt{/}\underbrace{\texttt{ssz\_snappy}}_{\text{encoding}} \]

    The bytes are the SSZ encoding of the request, prefixed by its uncompressed length as a varint and compressed in Snappy's framing format. Each response chunk starts with a result byte (0 for success, 1 invalid request, 2 server error, 3 resource unavailable), then, for objects whose type depends on the fork, the 4-byte fork digest, then the same length-and-Snappy encoding. Figure 23 builds a real request byte by byte.

    Figure 24 lists the current protocols, grouped by purpose.

    Each protocol has limits a server enforces: at most 128 blocks per request, at most 2 concurrent requests per protocol per peer, 5 s to the first byte and 10 s per chunk. Blocks must be served for 33,024 epochs (about five months) and data columns for 4,096 epochs (about 18 days); after that, blob data may be deleted.

    9Blobs and PeerDAS

    Rollups post their data to Ethereum in blobs (EIP-4844, March 2024). A blob is 4,096 field elements of 32 bytes, 128 KiB, committed to with a KZG commitment: a 48-byte fingerprint of the blob's polynomial, against which a short proof can show the polynomial's value at any single point. The block includes the commitments. Until Fusaka every node downloaded every blob, which capped the count at 6 per block target and 9 maximum. Since Fusaka (3 December 2025) and its two blob-parameter forks, mainnet allows a target of 14 and a maximum of 21 per block, and no node downloads them all. The mechanism is PeerDAS (EIP-7594).

    PeerDAS rests on erasure coding. A blob is the evaluations of a polynomial of degree below 4,096; evaluating the same polynomial at 4,096 more points doubles the blob to 8,192 elements, and any 4,096 of the 8,192 determine the polynomial. The extended blob is cut into 128 cells of 64 elements (2,048 bytes), each with a 48-byte KZG proof that it belongs to the blob's commitment. Cell \(i\) of every blob in the block forms column \(i\). Figure 25 builds the columns of one block.

    Example 2 · The size of one column at 21 blobs

    1. Cells: \(21 \times 2048 = 43{,}008\) bytes.
    2. Cell proofs and blob commitments: \(21 \times 48 + 21 \times 48 = 2{,}016\) bytes.
    3. Signed block header \(208\), inclusion proof \(4 \times 32 = 128\), column index \(8\), SSZ offsets \(3 \times 4 = 12\): \(356\) bytes.
    4. Total: \(43{,}008 + 2{,}016 + 356 = 45{,}380\) bytes. All 128 columns: 5.8 MB, against 2.75 MB of raw blobs, because of the 2× extension.

    Each column has its own gossip topic, data_column_sidecar_{i} for \(i = 0, \dots, 127\). A node subscribes only to the columns it custodies, and the assignment is a function of the node ID, so that peers can predict it.

    Definition 6 · Custody

    A node with custody count \(c\) stores the columns \(\{g_1, \dots, g_c\}\) found by hashing \(\mathrm{id}, \mathrm{id}+1, \mathrm{id}+2, \dots\): \(g = \mathrm{uint64}(\mathrm{sha256}(\mathrm{id}+j)[0{:}8]) \bmod 128\), skipping repeats. Every node has \(c \ge 4\). A node running validators with total balance \(B\) has \(c = \min\big(128, \max(8, \lfloor B / 32\,\text{ETH} \rfloor)\big)\), so at 4,096 ETH it stores everything (a supernode). The count is published as cgc in the ENR and in metadata/3.

    Why does storing a few columns let a node trust that the whole block's data was published? Because a proposer who withholds data must withhold a lot of it. With 64 or more of the 128 columns anyone can rebuild every blob, so data is lost only if at most 63 columns are available. A node checks at least \(\max(8, c)\) columns (SAMPLES_PER_SLOT = 8) and treats the block as available only if it obtains all of them. Node IDs are random, so across the network the custody columns are spread at random, and the question becomes: what fraction of nodes can a proposer fool? If at most 63 columns exist, a node whose 8 columns are a random choice sees all 8 with probability

    \[ \frac{\binom{63}{8}}{\binom{128}{8}} = 0.00271. \]

    So withholding fools about 0.27% of nodes. Figure 27 lets you vary both numbers. The bound is about the fraction of all nodes, not one node: custody columns are derived from the public node ID, so a proposer can target one node by publishing exactly its columns. And Fulu's nodes get their columns from their custody subscriptions; asking random peers for random columns every slot (peer sampling) is not part of Fulu.

    One more shortcut matters for speed. Most blob transactions reach the proposer's mempool before the block, and through the EL mempool they reach most other nodes too. So when a consensus client sees a new block (or its first column), it asks its own execution client with engine_getBlobsV2 for the blobs listed in the block. If the EL has all of them, the CL computes every column locally, without waiting for gossip, and republishes the columns it custodies. This is distributed blob publishing, shown in Figure 28: the proposer's upload of 128 columns is no longer the bottleneck, because many nodes publish them at once.

    10The Engine API: the bridge inside a node

    The two halves of a node meet over the Engine API: JSON-RPC over HTTP, by default on port 8551, usually on the same machine. The CL drives; the EL answers. Payloads and blobs travel as hexadecimal text inside JSON, so a 128 KiB blob takes 256 KiB on this link. Every call carries a JSON Web Token signed with HMAC-SHA256 under a 32-byte secret both clients read from a file, and the token's issue time must be within 60 seconds of the EL's clock, so a stolen token expires quickly.

    \[ \underbrace{\texttt{eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9}}_{\{\text{"alg":"HS256","typ":"JWT"}\}}\,.\,\underbrace{\texttt{eyJpYXQiOjE3NjE0MDAwMDB9}}_{\{\text{"iat":1761400000}\}}\,.\,\underbrace{\class{c-red}{\texttt{8Cp0zbpu…ndaE}}}_{\text{HMAC-SHA256 under the }\class{c-red}{\text{secret}}} \]

    Four methods do almost all the work in a slot, and Figure 29 places them. engine_forkchoiceUpdatedV3 tells the EL which block is the head, which is safe and which is finalized; with payload attributes attached (timestamp, fee recipient, randomness, withdrawals) it also tells the EL to start building a block, and returns a payload ID. engine_getPayloadV5 fetches the built payload and, since Osaka, a BlobsBundleV2 with the blobs, their commitments and 128 cell proofs per blob. engine_newPayloadV4 hands a received payload to the EL to execute, and the answer VALID, INVALID or SYNCING decides whether the CL may treat the block as valid. engine_getBlobsV2 is the mempool lookup of Section 9.

    11Outside the peer-to-peer protocol

    Builders and relays

    Most proposers do not build their own blocks. Specialised builders assemble the most profitable block, and relays stand between them and proposers. This market runs on plain HTTPS, entirely outside both peer-to-peer networks, through a sidecar program called MEV-Boost that speaks the builder API. The proposer registers its fee address once; in its slot it asks every configured relay for the best header (the block without its transactions), signs the chosen header without seeing the transactions (a blinded block), and sends the signature back; the relay then publishes the full block. The proposer has to trust the relay to publish, and the builder has to trust the relay not to steal the block's contents.

    Glamsterdam's enshrined proposer–builder separation (ePBS, EIP-7732), on public testnets in October 2026 with mainnet targeted for December but not yet scheduled, moves this exchange onto the consensus gossip network. Builders publish signed bids on execution_payload_bid; the proposer's block commits to one bid; the builder reveals the payload on execution_payload; and a payload timeliness committee of 512 validators votes on payload_attestation_message whether the payload arrived in time. Toggle Figure 30 between the two.

    Light clients

    A light client follows the chain without downloading blocks. It trusts one recent block root, and from then on it trusts the sync committee: 512 validators, replaced every 256 epochs (about 27 hours), who sign the head every slot. Each committee signs the next committee's public keys, so a light client walks forward one period at a time. Figure 31 shows the chain of trust and the messages that carry it.

    Execution-layer light clients and pre-Merge history are served by the Portal network, a separate distributed hash table running over discv5's TALKREQ, and by archive files (era and era1) on ordinary web servers. Neither is part of the eth protocol.

    12Sizes and deadlines

    The design choices above follow from sizes and from time. Figure 32 puts every object on one logarithmic axis, from a 240-byte vote to the 16.7 MiB RLPx frame limit. The two smallest limits sit at the bottom of the stack: a node record must fit 300 bytes and a discovery packet 1,280.

    Time is the other constraint. A slot is 12 seconds. Votes are due at 4 s, a third of the way in, so the block and its columns must reach most nodes, be validated and be executed before then. Aggregates are due at 8 s. Figure 33 lays the slot out. Every hop of gossip spends part of the 4-second budget on transfer and on validation, and every extra kilobyte per message spends more of it. A protocol that finalizes faster, such as the design in the decoupled consensus lesson, shortens these deadlines or adds voting rounds inside them, which is where the networking stack meets consensus design.

    13Where the stack strains

    The stack carries mainnet today, and the blob target rose from 6 to 14 per block in a year. It grew by accretion, though, and a redesign starts from a list of what that left behind. Figure 34 marks the towers of Figure 2 with four kinds of strain.

    • Duplication. Two stacks, two node keys, two peer lists, two discovery protocols on the EL alone, two serialisations (RLP and SSZ), two Snappy modes (block and framed), two handshakes with different ciphers, and a local HTTP bridge that encodes blobs as hex text.
    • Size caps. 300 bytes per record and 1,280 per discovery packet are fine for 33-byte keys and 64-byte signatures. They are not fine for the next generation of keys (Figure 35). Gossipsub forwards whole messages up to \(D\) times, which was cheap for votes and is expensive for columns.
    • Quantum-breakable cryptography. Every authentication in the stack uses elliptic curves: secp256k1 node keys (ENR signatures, discv4 packets, discv5 ID signatures and ECDH, RLPx ECIES, libp2p identity), X25519 in Noise, ECDHE in QUIC's TLS, BLS on every consensus message, and KZG pairings on blobs. A large quantum computer would let an attacker forge node identities and impersonate peers, and forge validator signatures.
    • Legacy kept alive. discv4, enode URLs, dead eth message numbers, mplex in the specification and RLPx's shared keystream stay because removing them needs every client to move at once.

    Figure 35 makes the size problem concrete. Each bar is a key, signature or key-exchange message that a post-quantum stack would carry, next to what the stack carries now and the limits it must fit. The NIST lattice signature ML-DSA-44 has a 1,312-byte public key, more than four ENRs, and a 2,420-byte signature, almost two discovery packets. A single attestation with such a signature grows from 240 to 2,564 bytes, 10.7×. Hash-based signatures, the candidates for Ethereum's post-quantum consensus (see the SPHINCS+ lesson), are larger still per signature and rely on aggregation to stay affordable.

    What to remember

    1. An Ethereum node is two clients with two peer-to-peer stacks. Transactions and history travel on the execution layer's devp2p; blocks, blob columns and votes travel on the consensus layer's libp2p. The Engine API joins them inside the machine.
    2. Both stacks find peers with Kademlia over UDP, keyed by \(\mathrm{keccak256}\) of a secp256k1 public key, and describe themselves with signed records of at most 300 bytes. The consensus layer filters records by the subnets and columns they advertise.
    3. RLPx (ECIES, AES-CTR, Keccak MACs, message numbers by offset) and libp2p (multistream-select, Noise or TLS-in-QUIC, yamux streams) build the same channel two different ways.
    4. The execution layer pushes transactions to a few peers and announces them to the rest; blob transactions are only announced. History comes by request, and state by snap ranges patched with access lists.
    5. The consensus layer gossips on topics stamped with a fork digest. Messages are identified by a 20-byte SHA-256 of their content; votes go through 64 subnets and 16 aggregators per committee.
    6. PeerDAS extends every blob 2× and splits it into 128 columns; each node stores at least 4 (8 with validators) chosen by hashing its ID. Data is recoverable from any 64 columns, and the Engine API's getBlobsV2 lets nodes build columns from their own mempool.
    7. The stack's limits are duplication, small hard size caps at the bottom, full-message amplification in gossip, and elliptic-curve cryptography on every floor.
