Ethereum serialization from zero

    Recursive Length Prefix

    How Ethereum writes a tree of byte strings as one flat run of bytes, and why exactly one run of bytes decodes back to each tree.

    You need: bytes written in hexadecimal (0x83 is 131), and the idea of a list.
    You will build: RLP encoding and decoding by hand, and the five near-miss encodings a correct decoder must reject.

    1Flattening loses the shape

    A transaction, a block header and a network message are each a list. Some fields are byte strings, and some fields are lists themselves. To hash such an object or send it over a wire, a client must turn it into one flat sequence of bytes. Another client must then recover the same object from those bytes.

    The obvious attempt writes the bytes of every string one after the other. Figure 1 tries it on two different trees and gets the same four bytes from both. Once the brackets are gone, no decoder can tell which tree it was given.

    RLP, short for Recursive Length Prefix, is the repair. Before each piece it writes what kind of piece it is and how many bytes it covers. The left tree in Figure 1 becomes ten bytes. This tree runs through the whole page, so its ten bytes are worth a first look now. By the end of Section 5 you will produce them yourself.

    2What RLP encodes

    RLP knows two kinds of object, and nothing else. It has no integers, no text and no field names. Those belong to the protocol that uses RLP.

    Definition 1 (item)

    An item is either a string, which is a finite sequence of bytes, or a list, which is a finite sequence of items.

    This page writes a string as [01 02 03] and a list as ⟨ … ⟩, the notation of Coglio's paper.

    "String" here means bytes, as in the Yellow Paper and on ethereum.org. It is not text. The definition is recursive, because a list contains items and an item can be a list. That recursion is the R in RLP. Figure 2 shows the three smallest cases. The empty string, the empty list, and a list that holds the empty string are three different items with three different encodings.

    3The first byte is a map

    A decoder that has just started reading an item sees one byte. That byte must tell it three things: whether a string or a list follows, how long it is, or where to find the length. RLP splits the 256 possible byte values into five ranges, one per case. Figure 3 colours each value by its range.

    Each range is a whole interval, so a decoder needs only four comparisons to classify a byte. Within a range, the distance from the start of the range is a count. In 83, the distance from 80 is 3, so a string of 3 bytes follows. The next four sections turn each range into a rule.

    4Encoding a string

    Start with the string dog, the bytes 64 6f 67. Its length is 3. Figure 4 builds its encoding in four steps.

    One case gets a shortcut. A string that is one byte below 0x80 is written as that byte alone, with no prefix. The byte 0f encodes as 0f. Single bytes below 0x80 include every ASCII character, and they are common, so the shortcut saves a byte each time. The decoder can still tell the cases apart, because a byte below 0x80 never starts any other encoding (Figure 3).

    Type into Figure 5 to see both cases. Then try a string of 55 characters, and one of 56.

    Long strings

    The short form has a limit. The short-string range 80–b7 holds 56 values, for lengths 0 to 55. A longer string needs its length written out in bytes. RLP writes the length in base 256, most significant byte first, with no leading zero byte.

    Definition 2 (big-endian length)

    For a whole number \(n \ge 1\), \(\class{c-purple}{\mathrm{BE}(n)}\) is the shortest byte sequence \(b_1 \dots b_k\) with \(n = \sum_i b_i \cdot 256^{k-i}\). For example, \(\mathrm{BE}(1024) = \)0400, because \(1024 = 4 \cdot 256 + 0\). By convention \(\mathrm{BE}(0)\) is the empty sequence.

    A long string's prefix byte then says how many length bytes follow. Figure 6 does this for a 1024-byte string. Drag the slider to try other lengths.

    The two forms and the shortcut make up the whole string rule. Here it is in the Yellow Paper's notation. A dot means concatenation, and \(\|x\|\) is the length of \(x\) in bytes.

    Definition 3 (string encoding, Yellow Paper Appendix B)

    \[ R_b(\class{c-yellow}{x}) = \begin{cases} \class{c-yellow}{x} & \text{if } \|x\| = 1 \text{ and } x[0] < 128 \\[2pt] \underbrace{\class{c-orange}{(128 + \|x\|)}}_{\text{prefix}} \cdot \class{c-yellow}{x} & \text{else if } \|x\| < 56 \\[2pt] \underbrace{\class{c-orange}{(183 + \|\mathrm{BE}(\|x\|)\|)}}_{\text{prefix}} \cdot \underbrace{\class{c-purple}{\mathrm{BE}(\|x\|)}}_{\text{length}} \cdot \class{c-yellow}{x} & \text{else if } \|x\| < 2^{64} \end{cases} \]

    A string of \(2^{64}\) bytes or more has no encoding. Section 8 shows where that limit comes from.

    The constants are the starts of the ranges in Figure 3: \(128 = \mathtt{0x80}\), and \(183 = \mathtt{0xb7}\), one below \(\mathtt{0xb8}\). Table 7 shows the header at each boundary.

    What is the header of a string of 300 bytes?

    \(300 \ge 56\), so use the long form. \(300 = 1 \cdot 256 + 44\), so \(\mathrm{BE}(300) = \mathtt{01\,2c}\), which is 2 bytes. The prefix is \(\mathtt{0xb7} + 2 = \mathtt{0xb9}\). The header is b9012c. Type 300 characters into Figure 5 to confirm.

    5Encoding a list

    A list is encoded in two steps. First, encode each item and join the encodings in order. That joined run of bytes is the payload. Second, put a prefix in front that gives the payload's length. The prefix uses the list ranges of Figure 3. Figure 8 encodes the list ⟨cat, dog⟩.

    Definition 4 (list encoding, Yellow Paper Appendix B)

    For a list \(x = \langle x_1, \dots, x_n \rangle\), let the payload be \(s(x) = \mathrm{RLP}(x_1) \cdot \ldots \cdot \mathrm{RLP}(x_n)\). Then

    \[ R_l(x) = \begin{cases} \class{c-blue}{(192 + \|s(x)\|)} \cdot s(x) & \text{if } \|s(x)\| < 56 \\[2pt] \class{c-blue}{(247 + \|\mathrm{BE}(\|s(x)\|)\|)} \cdot \class{c-purple}{\mathrm{BE}(\|s(x)\|)} \cdot s(x) & \text{else if } \|s(x)\| < 2^{64} \end{cases} \]

    \(\mathrm{RLP}(x)\) is \(R_b(x)\) when \(x\) is a string and \(R_l(x)\) when \(x\) is a list. A list fails to encode if any item fails.

    The list rule mirrors the string rule, with 192 (0xc0) and 247 (0xf7) in place of 128 and 183. It has no single-byte shortcut, because a list always has a prefix.

    The definition calls itself: to encode a list you first encode its items. So encoding runs from the leaves up. Figure 9 encodes the running tree this way and draws a bracket over each payload.

    Figure 9 is the whole idea of RLP in one picture. Every prefix states how far its item reaches. A list's bracket contains its items' brackets, and they never partly overlap. The tree is still in the bytes, as nested intervals.

    Example 1 (the running tree)

    1. [01 02 03] has 3 bytes: \(\mathtt{0x80} + 3 = \mathtt{83}\), giving 83 01 02 03.
    2. The empty list has an empty payload: \(\mathtt{0xc0} + 0 = \mathtt{c0}\).
    3. The inner list's payload is 83 01 02 03 c0, 5 bytes: \(\mathtt{0xc0} + 5 = \mathtt{c5}\).
    4. [ff] is one byte, but \(\mathtt{ff} \ge \mathtt{0x80}\), so the shortcut does not apply: 81 ff.
    5. The empty string is 80.
    6. The outer payload is \(6 + 2 + 1 = 9\) bytes: \(\mathtt{0xc0} + 9 = \mathtt{c9}\). The result is c9 c5 83 01 02 03 c0 81 ff 80.

    Check: this matches Figure 1 in Coglio's paper, which gives the bytes in decimal as 201, 197, 131, 1, 2, 3, 192, 129, 255, 128.

    Encode ⟨ ⟨⟩, ⟨⟨⟩⟩, ⟨ ⟨⟩, ⟨⟨⟩⟩ ⟩ ⟩.

    From the leaves up: \(\langle\rangle \to\) c0. \(\langle\langle\rangle\rangle \to\) c1 c0. \(\langle\langle\rangle, \langle\langle\rangle\rangle\rangle\) has payload c0 c1 c0, 3 bytes, so it is c3 c0 c1 c0. The outer payload is c0, c1 c0, c3 c0 c1 c0, which is \(1 + 2 + 4 = 7\) bytes. The answer is c7 c0 c1 c0 c3 c0 c1 c0, the "set-theoretic three" on ethereum.org. Paste it into Figure 12 to see the tree.

    6Integers are strings

    RLP has no integer type. Ethereum encodes a nonce, a balance or a gas limit by first turning the number into a string with \(\mathrm{BE}\) (Definition 2), then encoding that string. Zero becomes the empty string, so the integer 0 encodes as 80. Figure 10 shows a handful.

    The last card in Figure 10 is a trap. The string 00 04 00 is a valid RLP string. Read as an integer, it has a leading zero. ethereum.org states that a protocol reading integers must treat leading zeros as invalid. So the check happens one layer above RLP, when a field is interpreted as a number.

    7Decoding: read a byte, then jump

    A decoder reverses Figure 9 from the left. It reads one prefix, looks it up in Figure 3, and learns the kind and the extent of the next item. A string's bytes are copied without being read as prefixes. A list's payload is decoded the same way, item by item, until its length is used up. Figure 11 runs this on the running example.

    Decoding can also fail. A prefix may promise more bytes than remain. An item may cross the end of its list. Bytes may be left over after the top item. Figure 12 is a full decoder. Paste any hex, or pick a preset.

    8One item, one encoding

    Look at the decoder's presets marked "near miss". Each has a prefix and a length that point at real bytes. A careless decoder would accept them. Coglio found five such forms (2020, §4.2.1) while proving his decoder correct in the ACL2 theorem prover. A correct decoder must reject all five. Figure 13 lists them.

    Why reject bytes whose meaning is plain? Because Ethereum hashes RLP bytes. The Yellow Paper defines a block's hash as the Keccak-256 hash of its RLP-encoded header. If 81 05 and 05 both decoded to the same item, that item would have two hashes. Coglio gives a second case: a database keyed by encodings would store one item twice. The encoder never produces these forms. If the decoder accepts only what the encoder produces, then every item has exactly one encoding.

    Coglio reports that the Python reference decoder on the Ethereum wiki once accepted these forms, and that some client libraries did too. His work led to a fix on the wiki and to tests for all five forms in the shared ethereum/tests suite.

    Why a decoder never guesses

    Two properties make RLP decodable. Coglio proves both in ACL2.

    Theorem 1 (Coglio 2020, Fig. 5)

    Injective. If two items have the same encoding, they are the same item.

    Prefix-free. If one valid encoding is a prefix of another valid encoding, the two are equal.

    The second property is why the decoder in Figure 11 can stop the moment an item is complete, with no end marker. Figure 14 shows the proof idea. The first few bytes of an encoding fix its total length.

    In the long forms the length takes a few more bytes to read, but the argument is the same. The prefix gives the number of length bytes, those bytes give the payload length, and the total is fixed before the payload begins. That is also where the \(2^{64}\) limit of Definition 3 comes from. Write \(ll\) for the number of length bytes. Figure 15 counts the prefix values available for \(ll\).

    The arithmetic is direct. Eight length bytes reach at most

    \[ 256^8 - 1 = 2^{64} - 1 = 18\,446\,744\,073\,709\,551\,615 . \]

    No real object comes near that limit. It exists so that the five ranges of Figure 3 fit in one byte, with no value left over and no value shared.

    9The whole picture

    Figure 16 replays the decoding of the running example against the first-byte map. Each prefix byte lands in its range. The string content bytes are never looked up.

    What to remember

    An RLP item is a string of bytes or a list of items. Nothing else is encoded, and integers become big-endian strings with no leading zero.

    Every item starts with one byte that names its kind and its length, or the number of bytes that hold its length. A single byte below 0x80 is its own encoding.

    A list's length counts the bytes of its encoded items, so the brackets nest and decoding is a left-to-right walk with no lookahead.

    Every item has exactly one valid encoding. A decoder must reject the five near-miss forms, because Ethereum hashes these bytes.
