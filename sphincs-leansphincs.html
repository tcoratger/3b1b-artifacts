Post-quantum signatures for Ethereum

    SPHINCS+ and leanSphincs

    A signature scheme built from nothing but a hash function. Hash chains sign digits, a Merkle tree gathers the keys under one root, and a few-time layer lets the signer forget which keys it already used. leanSphincs is a version of it tuned for Ethereum.

    The 30-second version

    1. A one-time signature reveals points on hash chains. Hashing only goes forward, so fixing the sum of the signed digits stops forgeries.
    2. A Merkle tree puts \(2^{h}\) one-time keys under a 32-byte public key.
    3. SPHINCS+ picks the leaf by hashing the message, so the signer keeps no counter. Leaves then get reused, so the message is signed by FORS, which survives a few uses. The leaf's one-time key only ever signs FORS's fixed public key.
    4. leanSphincs uses one tree of height 26, FORS with 24 trees of height 10, and WOTS+C. A signature is 5,684 bytes, verifies in 373 BLAKE2s compressions, and a key lasts up to \(2^{30}\) signatures. Pruning builds only part of the tree, so a hardware wallet can generate a key in about a minute.
    You need: a hash function \(H\). It maps any input to a short string (16 bytes here), it is fast to compute, and nobody can run it backwards or find two inputs with the same output.
    You will build: a SPHINCS+ signature, piece by piece, and the parameter choices behind leanSphincs.

    1Why hash-based signatures

    Ethereum signs with ECDSA and BLS. Both rely on the discrete-logarithm problem on elliptic curves, which Shor's algorithm solves on a large quantum computer. A hash-based signature relies only on \(H\) being one-way and collision resistant, and no known quantum algorithm breaks that faster than brute force. The cost is size: an ECDSA signature is 65 bytes, a leanSphincs signature is 5,684.

    Every piece below is made of the same operation, so verification cost is counted in calls to \(H\), here 64-byte compressions of BLAKE2s or permutations of Keccak.

    2Signing a digit with a hash chain

    Pick a random secret \(\class{c-red}{x_0}\) and hash it again and again. Publish only the top. Figure 1 builds a chain of length \(w = 4\) with real SHA-256 values, truncated to four hex digits.

    Definition 1 · Winternitz one-time signature (WOTS)

    Hash the message to \(\ell\) digits \(\class{c-yellow}{d_1,\dots,d_\ell}\) in base \(w\). Use one chain per digit. The signature reveals \(x_{i,d_i}\) on chain \(i\). The verifier hashes it \(w-1-d_i\) more times and compares the tops with the public key.

    Figure 1 shows the flaw: anyone can raise a digit. The repair is to accept only digit vectors whose sum is a fixed target. Raising one digit then forces lowering another, and lowering means inverting \(H\). WOTS+ enforces this with extra checksum chains. WOTS+C drops them: the signer appends a counter \(c\) to the message and tries \(c = 0, 1, 2, \dots\) until the digits hit the target. Figure 2 does this on four chains with target sum 6.

    leanSphincs uses 64 chains of length 4 with target sum 120. The average sum of 64 random digits is 96. Setting the target higher means the verifier walks only \(64 \cdot 3 - 120 = 72\) chain steps, while the signer tries about 830 counters, since a random digest hits the sum 120 with probability \(1/829\). The signature holds 64 chain values of 16 bytes, 1,024 bytes, plus a 4-byte counter.

    3Many keys under one root

    A WOTS key signs once. To sign many times, generate \(2^{h}\) of them and hash their public keys pairwise into a Merkle tree. The root is the public key. A signature names a leaf, gives that leaf's WOTS signature, and adds the authentication path: the \(h\) sibling nodes the verifier needs to climb back to the root (Figure 3).

    4Forgetting which keys were used

    This tree, signed leaf by leaf with a counter, is XMSS. It is safe only if the signer never uses a leaf twice, which means storing the counter and never restoring an old backup. SPHINCS+ removes that state: the leaf index is read from a hash of the message and a randomizer \(R\). Figure 4 shows the price. Random picks collide long before the leaves run out; with \(2^{26}\) leaves the first repeat comes after the order of \(\sqrt{2^{26}} = 8{,}192\) signatures.

    The fix comes in two moves. First, the leaf's WOTS key no longer signs the message. It signs the public key of a second scheme attached to that leaf, and that public key is fixed, so a reused leaf signs the same value twice and leaks nothing new. Second, that scheme must be safe after a few signatures. It is FORS.

    Definition 2 · FORS (forest of random subsets)

    Take \(k\) Merkle trees of height \(a\) whose leaves are hashes of secrets. Hash the message with \(R\) and cut the digest into \(k\) indices of \(a\) bits. In tree \(j\), reveal secret number \(i_j\) and its authentication path. The FORS public key is the hash of the \(k\) roots.

    5How many signatures a key can make

    Suppose the FORS at one leaf has signed \(r\) times. A forger wants a new message whose \(k\) indices all point at secrets already revealed. In one tree that happens with probability \(1-(1-2^{-a})^{r}\), and the trees are independent:

    \[ \Pr[\text{forge at a leaf used } r \text{ times}] \;=\; \Big(\underbrace{1-\big(1-2^{-\class{c-orange}{a}}\big)^{r}}_{\text{one tree already open}}\Big)^{\class{c-orange}{k}} \]

    With \(k = 24\), \(a = 10\) and \(r = 16\), one tree is open with probability \(1.55\%\), and all 24 with probability \(2^{-144}\). If a key signs \(N\) times, the leaves receive \(N/2^{26}\) signatures each on average, scattered at random. Averaging the formula over that scatter gives the security in bits as a function of \(N\). The key's lifetime is the largest \(N\) that still keeps 127 bits (Figure 6).

    6The whole leanSphincs signature

    Figure 7 puts the pieces in order on the real parameters. The byte counter adds each part as the verifier consumes it. The message chooses the leaf and the FORS indices; FORS yields a public key; WOTS+C signs that key; the path climbs 26 levels to the root.

    The standard SLH-DSA (FIPS 205) stacks the tree differently. SLH-DSA-128s is a hypertree of 7 layers of height 9: each layer's WOTS key signs the root of the layer below, so a signature carries 7 WOTS signatures. Layers keep key generation small for \(2^{64}\) signatures. leanSphincs targets \(2^{30}\), so one layer of height 26 is affordable and saves six WOTS signatures. Figure 8 compares the sizes.

    The fourth bar replaces FORS with a two-level forest of small WOTS keys (6 chains of length 5, target sum 5): 25% smaller and 18% cheaper to verify at the same signing cost. The idea came from Jonas Nick's submission to sig.golf. That leaderboard scores hash-based schemes by bytes times verification cycles and checks each entry's 127-bit security in Lean. On 22 October 2026 its smallest entry was 5,216 bytes and its best product 36,479,157 byte·cycles.

    7Pruning: build only part of the tree

    Generating a full key means building all \(2^{26}\) leaves, each a WOTS+C key: about \(16 \cdot 10^{9}\) compressions, 16 seconds on a laptop and about 6 days on a hardware wallet. Conduition's hypertree pruning builds one subtree of \(2^{b}\) leaves and fills the \(26 - b\) missing siblings above it with pseudorandom surrogate values. The root looks like any other public key. Figure 9 runs it on a toy tree.

    Each retry costs one compression, \(2^{26-b}\) of them on average, and every FORS sees \(2^{26-b}\) times more signatures, which moves the curve in Figure 6 to the left. The leanSphincs note picks three points on that trade:

    Pruning is new and, per its author, not yet peer reviewed. One risk is that a signer reuses the same seed with two different pruning parameters. The note's fix is to derive the working seed as \(H(\text{seed} \,\|\, b)\), so each choice of \(b\) gives an unrelated key.

    8What to remember

    • Hash chains sign digits; a fixed digit sum (WOTS+C) blocks forgeries.
    • A Merkle tree turns many one-time keys into one public key, at \(h\) hashes per signature.
    • Statelessness forces leaf reuse, so the leaf signs a fixed FORS key and FORS signs the message.
    • Lifetime is set by how many FORS secrets leak: \(k = 24\), \(a = 10\) and \(h = 26\) give about \(2^{30}\) signatures at 127 bits.
    • leanSphincs: 5,684 bytes (4,276 with the WOTS forest), 373 compressions to verify, and pruning to trade lifetime for keygen time.
